## 3.2. Requisitos Não-Funcionais

| **ID** | **Descrição** |
| --- | --- |
| RNF001 | As funcionalidades do sistema devem ser expostas por meio de um web service, consumido de forma idêntica pelos clientes web e móvel. |
| RNF002 | O sistema deve estar disponível em ambiente web e em ambiente móvel, com paridade das funcionalidades essenciais entre as duas plataformas. |
| RNF003 | O cliente móvel deve ser construído em tecnologia híbrida/multiplataforma, a partir de uma base de código única. |
| RNF004 | As notificações de eventos compatíveis com o perfil do usuário devem ser propagadas aos clientes conectados em tempo real, sem necessidade de recarregamento manual ou consulta periódica pelo cliente. |
| RNF005 | O sistema deve suportar múltiplos clientes conectados simultaneamente ao mesmo servidor, executando operações concorrentes sobre a mesma base de eventos sem inconsistência de dados. |
| RNF006 | Cada cliente deve receber apenas as atualizações correspondentes aos seus interesses, de modo a não consumir tráfego com mensagens irrelevantes. |
| RNF007 | O sistema deve tratar falhas de comunicação, timeouts e indisponibilidade de serviços, aplicando políticas de reenvio automático de requisições no cliente e no servidor. |
| RNF008 | O servidor deve interromper temporariamente as chamadas a serviços que apresentem falhas recorrentes, de modo a impedir a propagação de erros e permitir a sua recuperação. |
| RNF009 | O sistema deve possuir cobertura de testes em nível unitário, de integração e ponta a ponta, contemplando as plataformas web e móvel. |
| RNF010 | A aplicação deve ser hospedada em serviços de nuvem de plano gratuito, com implantação automatizada a partir do repositório Git. |
| RNF011 | Os tipos de dados trocados entre cliente e servidor devem ser compartilhados entre as camadas, de modo a impedir divergências de contrato em tempo de desenvolvimento. |

## 3.3. Restrições Arquiteturais

As restrições impostas ao projeto que afetam sua arquitetura são:

- A comunicação entre os clientes e o servidor deve seguir o padrão **RESTful**;
- O back-end e os clientes devem ser desenvolvidos em **TypeScript**, permitindo o compartilhamento de tipos entre as camadas;
- O cliente web deve ser desenvolvido em **React** e o cliente móvel em **React Native com Expo**, em base de código híbrida/multiplataforma;
- O processamento em tempo real deve ser realizado por meio de um **middleware de mensageria**, não sendo admitida a consulta periódica ao servidor (*polling*) como mecanismo principal de atualização;
- A persistência deve ocorrer em banco de dados relacional **PostgreSQL**;
- A hospedagem deve utilizar exclusivamente **serviços de nuvem com plano gratuito**;
- Toda a documentação do projeto deve ser mantida em **Markdown**, publicamente acessível no repositório do GitHub.

### Justificativas das decisões arquiteturais

As decisões acima foram tomadas pela equipe considerando o atendimento aos requisitos obrigatórios da disciplina, a curva de aprendizado do grupo e a existência de planos gratuitos. As justificativas de cada escolha são:

| Requisito obrigatório | Decisão do grupo | Justificativa |
| --- | --- | --- |
| Modelo Web Service (REST / GraphQL / gRPC) | **REST** | Padrão simples e amplamente conhecido, fácil de documentar e testar, com boa curva de aprendizado para o grupo. |
| Stack Back-end | **TypeScript** | A tipagem estática reduz erros em tempo de desenvolvimento e permite compartilhar tipos com o front-end, que também utiliza TypeScript. |
| Stack Front-end Web | **React** | Biblioteca consolidada no mercado, com ampla comunidade e documentação, cuja componentização facilita a organização da interface. |
| Stack Mobile/Híbrido | **React Native + [Expo](https://expo.dev/)** | Reaproveita o conhecimento de React já existente na equipe; o Expo agiliza build e testes sem exigir a configuração de ambiente nativo Android/iOS. |
| Middleware de mensageria (tempo real) | **[Supabase](https://supabase.com/) (Realtime)** | Fornece canais de mensageria em tempo real prontos sobre o próprio PostgreSQL, dispensando a administração de um broker separado (como Kafka ou RabbitMQ). |
| Estratégia de concorrência (múltiplos clientes) | **Filtros de Canal (*Channel Filtering*)** | Cada cliente assina apenas os canais de seu interesse, o que reduz o tráfego desnecessário e permite que vários clientes recebam atualizações simultaneamente sem conflito. |
| Tratamento de erros (retry, timeout, circuit breaker) | **Web/Mobile: [TanStack Query](https://tanstack.com/query/latest) · Back-end: Cockatiel** | O TanStack Query cuida de cache, retry automático e revalidação nas requisições do cliente; o Cockatiel adiciona no servidor políticas de retry, timeout e circuit breaker de forma declarativa. |
| Estratégia de testes (unitário/integração/e2e) | **Unitário e integração: [Vitest](https://vitest.dev/) · E2E Web: Playwright · E2E Mobile: Maestro** | O Vitest é rápido e integra-se bem com TypeScript e React; o Playwright cobre fluxos completos no navegador; o Maestro é voltado especificamente a testes ponta a ponta em aplicações React Native. |
| Serviço de nuvem (hospedagem gratuita) | **Front-end: Vercel · Back-end: Render** | Ambos oferecem plano gratuito, deploy automático a partir do Git e boa integração com projetos Node/React. |
| Banco de dados | **PostgreSQL** | Banco relacional robusto e gratuito, já integrado nativamente ao Supabase, o que mantém mensageria e dados em uma mesma plataforma. |
